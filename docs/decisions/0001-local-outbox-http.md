# ADR 0001: local HTTP transport backed by PostgreSQL outbox/inbox

Status: accepted for the single-club deployment.

The club must continue operating when its Internet connection is down. Auth, Billing and Session already store state in local PostgreSQL. A local HTTP transport between the three API hosts uses those databases as durable queues and needs no cloud broker or provider account. Each host runs a dispatcher that polls committed outbox rows and posts a JSON event envelope to configured peers. The envelope carries a UUID, stable versioned event name, JSON payload and occurrence time. Event names such as `session.completed.v1` contain no .NET assembly identity.

The receiver writes an inbox receipt in the same local database transaction as its handler's state changes. Repeated delivery of the same UUID sees the receipt and does nothing. The sender marks an event delivered only after all configured peers acknowledge it. A lost HTTP acknowledgement causes a resend, which the inbox deduplicates. Failure increments a retry counter and schedules exponential backoff; five failures put the row in dead-letter (`DeadLetterAt`, last error retained). An operator must inspect and explicitly reset a dead-letter row for replay. Configure subscribers only on trusted local service addresses and set a distinct 32+ character `EVENT_TRANSPORT_KEY`; public ingress must block `/internal/*`. This header is a service credential, so local traffic must stay on the trusted container network or use TLS/mTLS if crossing machines.

Compared with hosted Kafka/RabbitMQ or a cloud queue, this adds no extra infrastructure for an offline club. The tradeoffs are polling latency (about two seconds), point-to-point fan-out, no cross-service atomic transaction, and a per-source single-dispatcher deployment assumption. For multiple replicas, add row claiming with `FOR UPDATE SKIP LOCKED` or move to a durable local broker. HTTP retries may resend to a peer that already acknowledged; inbox deduplication is required. Non-actionable events are recorded in peers' inboxes, enabling a future consumer to be deployed with explicit version handling, but they are not retroactively reprocessed.

Session starts require an immediate reservation response from Billing, so they use a synchronous internal HTTP command. Session completion and cancellation use the outbox because Billing settlement can wait for local service recovery. If Billing is unavailable at start, Session fails closed. The Session API compensates a failed local start by releasing the Billing reservation. A process crash between the remote reserve and local commit can leave a held reservation; this needs operational reconciliation against Session state before any automatic release. A held reservation is safer than an uncharged session. Manual release must verify there is no active session. A dead-letter `session.completed.v1` or `session.cancelled.v1` event blocks reconciliation until replayed.

The sender sends JSON over the trusted local network. The shared secret is not an Internet-facing authorization system. Rotating it requires coordinating all services. Event handlers must validate event versions and preserve unknown events in the inbox for observability; new business handlers need an explicit replay/backfill plan for historical events.
