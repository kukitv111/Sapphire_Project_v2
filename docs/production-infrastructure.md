# Production infrastructure and identity operations

The production overlay is [docker-compose.prod.yml](../docker-compose.prod.yml). It is a deployment template, not an instruction to point local tests at live data. Fill a private env file from `.env.prod.example`, set `SAPPHIRE_DOMAIN` to the certificate's DNS name, mount a backup filesystem independent of PostgreSQL data at `BACKUP_ROOT`, and install the real certificate and private key as `infra/proxy/certs/fullchain.pem` and `privkey.pem` (or replace that mount with the site secret store). Keep the key out of Git. The edge publishes only ports 80 and 443; API and database host ports are removed by the overlay. `/internal/*` is blocked at nginx. The proxy is assigned `172.28.48.10` on the overlay network; only this address is trusted for `X-Forwarded-*` by the APIs. Change both values together if the subnet conflicts with the host network. nginx rejects other Host values, overwrites client supplied forwarded IP and scheme headers, and applies per-IP request and connection limits; the existing in-process Auth limit remains.

Renew the certificate through the site's ACME or PKI workflow and reload nginx after replacement. The template does not ship a certificate issuer or a certificate; production deployment must supply both. The API Docker build was attempted in the local Linux engine. Base images eventually downloaded, but NuGet restore inside Docker hit a 60-second package-download timeout and the stalled build was stopped. Re-run image build in a network-capable build environment before release.

On **new empty volumes**, provision and deploy in this order:

```sh
docker compose -f docker-compose.yml -f docker-compose.prod.yml --env-file .env.prod build auth-api billing-api session-api
docker compose -f docker-compose.yml -f docker-compose.prod.yml --env-file .env.prod up -d --wait auth-db billing-db session-db
docker compose -f docker-compose.yml -f docker-compose.prod.yml --env-file .env.prod --profile migrate run --rm auth-migrate
docker compose -f docker-compose.yml -f docker-compose.prod.yml --env-file .env.prod --profile migrate run --rm billing-migrate
docker compose -f docker-compose.yml -f docker-compose.prod.yml --env-file .env.prod --profile migrate run --rm session-migrate
docker compose -f docker-compose.yml -f docker-compose.prod.yml --env-file .env.prod --profile bootstrap run --rm auth-bootstrap
docker compose -f docker-compose.yml -f docker-compose.prod.yml --env-file .env.prod up -d
```

The PostgreSQL first-boot script creates a separate runtime role without schema DDL and a schema-owning migration role per service. API connection strings use runtime roles; one-off migration jobs use migration roles. The script runs only on *empty* database volumes. Existing volumes require a reviewed role/grant migration. The bootstrap CLI is transactional and stores a one-time marker. Remove `BOOTSTRAP_ADMIN_PASSWORD` from the env file after it succeeds; a second bootstrap is rejected even after the original admin is deleted. The first admin may log in only to change the temporary password; all normal authenticated routes reject that token until the password is changed and a new login completes.

Each API validates signed JWTs and checks the user's current token version for every authenticated request. Auth reads its own database; Billing and Session call Auth's internal endpoint with the local transport credential and fail closed when Auth cannot be reached. Banning or changing a password increments the version, invalidating existing access tokens immediately after the write commits. Keep Auth on a low-latency local network and monitor its readiness. No positive revocation cache is used.

Structured JSON logs include `CorrelationId`, the edge passes `X-Correlation-ID`, and HTTP calls propagate it between services. A dispatched outbox event uses its event ID as the correlation ID. OpenTelemetry records inbound and outbound HTTP traces plus ASP.NET Core and Sapphire metrics to the local collector. Npgsql pool labels are intentionally not exported because the default pool name can contain a connection string; an explicit counter records pool-exhaustion exceptions. Prometheus evaluates readiness, dead-letter, 5xx and pool exhaustion alerts. Alertmanager writes notifications to the local `alert-log` volume and UI on loopback port 9093; connect its receiver to an operator-controlled notification destination before unattended operation. The local trace file and Prometheus storage also need retention and off-host export if they are part of incident evidence.

The backup sidecars run as UID/GID 70 and execute `pg_dump -Fc` every hour, publish a file only after the dump succeeds, and retain seven days at `BACKUP_ROOT/{auth,billing,session}`. Pre-create those three directories on the mounted backup filesystem, owned by 70:70 and mode 0700. Backups on the database's own disk do not survive host loss. Treat `BACKUP_ROOT` as an independently mounted and replicated destination; monitor `backup_complete` and absence of a new file for two hours. **Target RPO: at most one hour** while the backup loop and independent mount are healthy. **Target RTO: four hours**, including provisioning a new PostgreSQL instance, restoring all three dumps, running readiness checks and verifying key business records. A disposable Billing fixture was restored to a separate PostgreSQL container and compared for schema column count and key row counts; that small-fixture result does not prove the four-hour target for production data. Time a full-size restore before launch and repeat it quarterly.

To restore, provision a clean instance with PostgreSQL 16, create the target database, run `pg_restore --no-owner --no-acl -d <new_database> <latest.dump>`, compare migration history/schema and representative record counts with the manifest, then point a staging API at it for readiness and transaction checks. Restore all service snapshots from the same backup window; separately reconcile cross-service reservations and outbox state. Never run InitialCreate against a database created with `EnsureCreated`. First back it up, restore to a separate copy, compare its schema with generated migrations, and apply a reviewed baseline only to the copy before any live migration.

## Auth API breaking change

Register, login and refresh responses now expose `tokens.accessTokenExpiresAt` and `tokens.refreshTokenExpiresAt` as separate UTC values. The ambiguous `tokens.expiresAt` field is removed. The flat Auth response contract has the same replacement. Clients must deploy with the new fields; the admin React client types and first-password-change flow were updated, and the desktop DTO was updated. `user.mustChangePassword` tells clients to open the change-password route. The desktop UI remains a shell and does not implement that flow yet.

Access tokens issued before this change have no `token_version` claim and are rejected after deployment. Users must log in again or use a valid refresh token with a compatible client. Coordinate the backend and admin client rollout.
